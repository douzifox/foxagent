# FoxAgent 优化指导

> 背景:2026-08-04,Claude Code 通过 MCP 指挥 FoxAgent 完成《扫雷走位》原型(一次完整的真实协作)。本文档是指挥方视角的实战复盘 + 改造指导。
> 涉及文件:`src/mcp.ts`(MCP 服务器)、`src/cli.ts`(-p 单任务模式)、`src/agent.ts`(agent 核心)。
> 原则:保持现有极简手写风格,不引 SDK、不加框架。按优先级从上往下做,每一项独立可交付。

---

## 实战中暴露的问题(按出场顺序)

1. **环境变量断链**:MCP 服务器由 GUI 启动,读不到 ~/.zshrc;mcp.ts 只透传 `process.env`,导致 `loadConfig()` 报缺 FOXAGENT_* 三件套。当时靠"bun 自动加载 cwd 下 .env"绕过,但这把密钥复制进了业务项目目录,是权宜之计。
2. **同步阻塞**:`tools/call` 挂着等子进程跑完才返回,长任务期间调用方(和用户)只能干等,也无法中途打断。
3. **部分成功无法表达**:第一次任务实际全部完成,仅收尾时上游 API 503,但 cli.ts 里任何 error 事件都置 `exitCode = 1`,MCP 侧整个结果被标为 `isError: true`。成果和事故混在一个信号里,调用方容易误判"全失败"。
4. **无重试**:上游 503 时直接翻车,没有退避重试,也没有备用模型。第二次调用(返工单)颗粒无收。
5. **轨迹全量回传**:2 万+ 字符的完整轨迹塞进 MCP 结果,被客户端截断,关键信息(改了哪些文件、验证结果)淹没在过程里。
6. **单向沟通**:-p 模式下 `confirmCommand` 硬编码"一律拒绝"(cli.ts 的 runOnce)。交互模式明明有问真人 y/n 的能力,MCP 这条路上却没人接电话。遇到歧义它只能猜——本次它猜错过一次棋盘索引方向(转置 bug),遇到危险命令只能死路。

加分项(保持住):被安全策略拦下后会自己找替代方案(临时文件方案被拒后改用 `new Function` 内存编译验证语法)。

---

## P0:异步任务模型 + 双向沟通(核心改造)

一刀解决问题 2 和 6。把 mcp.ts 的单个 `foxagent` 工具拆成三个:

### 工具设计

| 工具 | 入参 | 返回 | 说明 |
|---|---|---|---|
| `fox_submit` | task, cwd, continueSession? | taskId | spawn 子进程后**立即返回**,不等待 |
| `fox_status` | taskId | state, newOutput, question? | state ∈ `running` / `waiting_for_input` / `done` / `failed`;newOutput 是**自上次查询以来的增量**输出(服务器端记 offset);waiting 时附上 question |
| `fox_reply` | taskId, answer | ok | 把回答送进子进程,状态回到 running |

mcp.ts 内存里维护一个任务表即可:`Map<taskId, { child, buffer, offset, state, question }>`。不需要持久化——MCP 服务器进程活着任务表就活着,进程没了任务也没了,如实报"任务不存在"即可。

### 子进程沟通协议(cli.ts 配合)

-p 模式的 cli 与 mcp.ts 之间用 stdio 走一个极简行协议:

- cli 侧:`runOnce` 的 `confirmCommand` 不再硬拒,改为——向 stdout 打印一行哨兵 JSON,如 `@@ASK@@{"type":"confirm","question":"要执行这条命令吗:rm -rf dist"}`,然后**等待 stdin 的一行回复**(y/n 或文本),拿到后继续。
- mcp.ts 侧:监听子进程 stdout,逐行扫描;遇到 `@@ASK@@` 开头的行,不计入输出 buffer,把任务状态置为 `waiting_for_input` 并存下 question;`fox_reply` 时向 `child.stdin` 写一行 answer + `\n`,状态回 `running`。
- 哨兵前缀要选正文里不可能自然出现的(如 `@@ASK@@`),并且只在行首匹配。

### 让 agent 能主动提问(沟通能力的完整版)

危险命令确认只是被动沟通。在 agent.ts 的工具集里加一个 `ask` 工具(描述:"拿不准的决策、发现任务描述有歧义或矛盾时,向指挥者提问,返回对方的回答"),实现复用上面同一条 stdin/stdout 通道(`{"type":"ask","question":...}`)。这样它遇到"棋盘索引到底是 g[y][x] 还是 g[x][y]"这类歧义时,可以问,而不是猜。

注意在系统提示里给它立规矩:能自己查清楚的不要问(读代码、跑命令验证优先),问题要带上下文和自己的倾向选项。别把提问变成甩锅。

### 交互模式不受影响

cli.ts 的交互模式(readline 那条路)完全不动。哨兵协议只在 `-p` 模式启用。

## P1:上游 API 重试

在调用模型的最外层(runAgent 里发请求处)加指数退避:503 / 429 / 网络错误时重试,建议 3 次,间隔 2s → 8s → 30s,重试时通过 onEvent 发一条 status 事件("上游繁忙,8 秒后重试 2/3")。可选:支持 `FOXAGENT_FALLBACK_MODEL`,重试耗尽后换备用模型再试一轮。

## P1:结构化收尾,区分"成果"与"事故"

runOnce 结束时输出一段机器可读的尾部摘要(单独一行 JSON,同样用哨兵前缀如 `@@RESULT@@`):

```json
{"filesChanged": ["index.html"], "verified": true, "outcome": "完成", "error": null}
```

- `filesChanged`:本轮 write/edit 过的文件清单(agent 核心里有事件流,汇总即可)。
- `error`:只放真正没干成的事。**干完活之后的收尾错误(如最后一次模型调用 503)不应把整趟活标成失败**——退出码的语义改为:0 = 任务主体完成,1 = 任务主体没完成。
- mcp.ts 把这段摘要放在返回内容最前面,完整轨迹跟在后面(见下一条)。

## P2:轨迹瘦身

完整轨迹写入 `<cwd>/.foxagent/runs/<taskId>.log`,MCP 结果只返回:结构化摘要 + 最后一条 assistant 文本 + 轨迹文件路径。调用方要细节自己去读文件。记得把 `.foxagent/` 加进它自己维护的 gitignore 建议里。

## P2:显式会话号

`--continue` 语义是"最近一次会话",多任务并行时会串线。session.ts 里 `loadSession(root, id)` 已经存在,只差暴露:加 `--session <id>` 参数;`fox_submit` 返回结果里带上本次 sessionId,后续任务想接着聊就显式传。

## P2:配置加载兜底

`loadConfig()` 读不到环境变量时,依次兜底:`~/.config/foxagent/env`(KEY=VALUE 格式)→ 报错。报错信息里加一句:"如果通过 MCP 调用,请在 MCP 注册配置的 env 字段里设置",因为 GUI 启动的进程读不到 shell 配置——这次就是栽在这里。

> 另:业主记得把 ~/.claude.json 里 foxagent 的 `env` 补上 FOXAGENT_* 三件套,然后删掉扫雷项目目录里的应急 .env。

## 验收清单

- [ ] `fox_submit` 一个 60 秒以上的任务,立即拿到 taskId;期间 `fox_status` 能看到增量输出。
- [ ] 让任务里包含一条会被拦的危险命令:状态变为 `waiting_for_input`,`fox_reply` 批准后继续执行。
- [ ] 给 agent 一个故意含歧义的任务(如"把配置里的超时改大一点"):它调用 `ask` 提问而不是瞎猜。
- [ ] 模拟上游 503(改 host 指向一个返回 503 的桩):能看到重试 status,3 次后才报错。
- [ ] 干完活后最后一步报错的场景:退出码为 0,`@@RESULT@@` 里 filesChanged 完整、error 单独呈现。
- [ ] MCP 返回体 < 2KB(不含轨迹),轨迹文件在 `.foxagent/runs/` 下可读。
- [ ] 交互模式(不带 -p)行为与改造前完全一致。
